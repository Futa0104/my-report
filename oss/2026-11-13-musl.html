01概要・基本情報・開発背景

muslはLinux向けのC標準ライブラリ実装です。C標準ライブラリ、POSIX API、スレッド、動的リンクなどを提供します。

項目内容
実装言語C・CPU依存のアセンブリ
ライセンスMITを中心とするライセンス（同梱文書参照）
対象Linuxユーザー空間
開発プロジェクトmusl libc

開発背景

小さな実行ファイルや静的リンクのしやすさ、標準への適合性、実装の簡潔さを重視するLinux向けlibcとして設計されました。動的リンカとスレッド機能を一体化する設計も、内部ABIの複雑さを減らす狙いがあります。設計思想（公式）

02特徴・使いどころ

  • 小さく追いやすい実装：libcの学習や組み込みLinuxに適する。
  • 静的リンクへの配慮：依存ライブラリをまとめたツールや軽量コンテナに向く。
  • 標準API：POSIXプログラムの移植性を確保しやすい。ただしglibc固有の拡張やABI互換性は個別に確認する。

05技術Pickup： read()とスレッドのキャンセル

今回の問い：終了要求を受けたスレッドが、データ待ちのまま永遠に止まっていたら、どうやって安全に終了させるのか。muslのキャンセルポイントは、OSのI/O機構だけでは満たせないPOSIXのAPI仕様をライブラリが実現する好例です。

1. なぜスレッドのキャンセルが必要なのか

例えば、受信スレッドAが空のパイプをread()で待ち続け、管理スレッドBがアプリの終了や通信停止を指示する状況を考えます。単に終了フラグを更新しても、Aはread()から戻るまでそのフラグを確認できません。反対に任意の命令で強制終了すると、確保したメモリや保持中のmutexなどが残り、共有データの整合性が崩れるおそれがあります。

終了フラグだけB：終了フラグを設定
↓
A：read()の待機は継続

データ到着などで待機を抜けるまで、フラグを確認できない。

遅延キャンセルB：pthread_cancel(A)
↓
A：キャンセルポイントで要求を処理
↓
A：後片付け・終了
↓
B：joinで終了を確認

キャンセルポイントは「いつでも安全に止められる場所」という保証ではありません。アプリ側が資源の所有権とクリーンアップを設計しておく必要があります。POSIXのキャンセル機構を使わず、終了フラグとpoll()/eventfdなどで待機解除を行う協調停止も選択肢です。

2. キャンセルポイントとは何か

pthread_cancel()は対象に終了要求を送るAPIであり、終了完了を保証しません。通常のキャンセル有効・遅延キャンセル設定では、POSIXが定めるキャンセルポイント（read()、pthread_cond_wait()、pthread_testcancel()など）で保留中の要求を処理します。ブロック中にも処理され得ます。キャンセル無効なら要求は保留され、非同期キャンセルはキャンセルポイント外でも終了し得ます。

重要なのは、カーネルから待機処理を抜けることと、read()の呼び出し元に戻り値を返すことは別だという点です。キャンセルが成立すると通常のread()の呼び出し元へは戻らず、スレッド終了処理に進みます。通常のシグナルによる中断ではEINTRを返す場合があります。実行済みのI/Oは巻き戻りません。

3. 停止要求から終了確認まで

read()で待機するスレッド1 / 4
スレッドAread()で待機
スレッドB通常実行

① 読み取り待ち

Aは空のパイプのread()でブロックする。

キャンセル有効・遅延キャンセルで、読み取りと競合せずキャンセルが成立する場合の概念例です。キャンセル要求がいつ成立するかは実行状態やI/Oの完了との競合に依存します。joinは終了前に呼んで待機することもできます。

4. サンプルコード：終了処理で何をするのか

ワーカースレッドが確保したバッファを、キャンセル時のクリーンアップハンドラで解放します。セマフォはハンドラ登録後に管理側へ準備完了を通知するためのものです。厳密にread()のカーネル待機に入ったことまでは保証しません。説明用に各APIのエラー処理を省略しています。

#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

static int fd[2];
static sem_t ready;

static void cleanup(void *p) {
    free(p);
    puts("worker: buffer freed");
}

static void *worker(void *arg) {
    char *buf = malloc(64);
    if (!buf) abort();
    pthread_cleanup_push(cleanup, buf);
    puts("worker: about to read");
    sem_post(&ready);
    read(fd[0], buf, 64);
    puts("worker: read returned");
    pthread_cleanup_pop(1);
    return NULL;
}

int main(void) {
    pthread_t t;
    void *result;
    pipe(fd);
    sem_init(&ready, 0, 0);
    pthread_create(&t, NULL, worker, NULL);
    sem_wait(&ready);
    puts("main: cancel requested");
    pthread_cancel(t);
    pthread_join(t, &result);
    puts(result == PTHREAD_CANCELED
         ? "main: canceled" : "main: other result");
    sem_destroy(&ready);
    close(fd[0]); close(fd[1]);
    return 0;
}
gcc -pthread cancel.c -o cancel
./cancel

実行結果（Linux / glibc 2.41で確認。muslでの実行ではない）

worker: about to read
main: cancel requested
worker: buffer freed
main: canceled

read returnedが表示されず、バッファが解放されてからjoinで終了を確認できます。終了時には登録されたクリーンアップハンドラ、スレッド固有データのデストラクタなどが実行されます。ただしmallocした領域や開いたファイル記述子がすべて自動解放されるわけではありません。

5. カーネル・libc・アプリの責務

層責務
アプリケーション停止要求を出す・資源の後片付けを登録・joinで終了確認
musl libcキャンセル状態、キャンセルポイントの判定、syscallとの協調、終了時の処理
LinuxカーネルI/Oの実行、待機、シグナル配送、スレッドの低レベルな終了機構

生のread syscallだけでは、POSIXのスレッドキャンセル契約をすべて実現できません。ここにlibcの存在意義があります。

6. muslの実装を追う

read()src/unistd/read.c
↓
syscall_cp(SYS_read, ...)キャンセル可能なsyscallの入口
↓
__syscall_cp_c() / CPU別コードキャンセル状態・要求を確認し、syscallを実行
↓
Linux read syscallデータ取得・待機・戻り値

別スレッドからのpthread_cancel()は対象のキャンセルフラグを設定し、内部シグナルSIGCANCELを送ります。pthread_cancel.cでは、シグナルハンドラが保存された命令位置を確認し、キャンセル可能区間（__cp_begin〜__cp_end）内なら__cp_cancelへ制御を移す仕組みを持ちます。また、syscallからEINTRが返った場合にもキャンセル状態を確認します。単なるフラグの前後確認では、フラグ確認直後からsyscallで待機するまでの競合を取りこぼす可能性があるためです。

CPU別の例：src/thread/x86_64/syscall_cp.s。キャンセル成立時の__cancel()は、通常の有効状態ならpthread_exit(PTHREAD_CANCELED)へ進みます。終了処理はsrc/thread/pthread_create.cの実装から追えます。詳しくはmusl公式の設計文書を参照してください。

設計上の意義：アプリが利用するAPIの契約を、OSが提供する機構とライブラリ固有の状態管理を組み合わせて成立させる。これはOSとミドルウェアの境界、並行処理の終了設計を学ぶうえで重要です。

06設計から学べること

  • 公開APIの契約と下位機構を分離する：Linuxのread syscallはI/Oを実行する。一方POSIX read()にはキャンセルポイントとしての振る舞いも必要。公開APIを単なる下位APIの転送と考えない。
    実装・資料：src/unistd/read.c · Design Concepts
  • 協調停止とリソースの所有権：停止要求、実際の終了、終了確認を分け、クリーンアップハンドラでアプリ固有の資源を解放する。
    実装・資料：src/thread/pthread_cancel.c · src/thread/pthread_create.c · POSIX pthread_cancel() · Linux man-pages（キャンセルの仕様）
  • 競合する境界の設計：キャンセルフラグの確認からsyscallに入るまでの競合を、CPU別のキャンセル可能区間とシグナル処理の協調で扱う。
    実装・資料：src/thread/pthread_cancel.c · src/thread/x86_64/syscall_cp.s · Design Concepts
  • CPU依存処理と移植性：syscallの呼び出し規約を分離する。glibc固有の拡張やABIを利用する場合は互換性を個別に確認する。
    実装・資料：src/internal/syscall.h · arch/ · glibcとの機能差
