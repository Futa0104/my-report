musl libc

POSIX APIとLinuxシステムコールの境界を読む。小さく堅牢なC標準ライブラリ。

概要

muslはLinux向けのC標準ライブラリ実装。C標準ライブラリとPOSIX API、スレッド、動的リンクなどの機能を提供する。C言語とアーキテクチャ依存のアセンブリで実装され、シンプルさ、標準への適合、静的リンクのしやすさを重視している。glibcとは異なるlibc実装であり、ABIやGNU拡張の互換性は個別に確認が必要。

主な特徴

  • 小さな実装：構成が比較的シンプルで、ソースコードを追いやすい。
  • POSIXインターフェース：open()、read()、pthread_create()などを提供する。
  • 静的リンク：依存をまとめた実行ファイルを作りやすい。
  • Linux向け：カーネルのシステムコールとユーザー空間のAPIを橋渡しする。

使いどころ

Linuxベースの組み込み機器、軽量なコンテナ、静的リンクしたツール、libcの実装学習。なお、musl自体はRTOSカーネルではなく、Linuxのユーザー空間で動作するライブラリ。

技術Pickup：read()はなぜ単なるsyscallではない？

Linuxのシステムコールはカーネルへの低レベルな入口だが、アプリケーションが使うread()はPOSIXライブラリ関数でもある。muslでは、スレッドのキャンセルに対応するため、read()の実装がキャンセル可能なシステムコール経路を利用する。

キャンセルポイントの意味

POSIXのread()はキャンセルポイント。スレッドに遅延キャンセル要求が保留されている場合、キャンセルが有効であれば、この地点でスレッドの終了処理が始まる可能性がある。したがって、単純に生のシステムコールを呼ぶだけでは、POSIXスレッドのキャンセル意味論を完全には満たせない。

概念例：

ssize_t n = read(fd, buf, sizeof buf);
/* ここまで戻る前にキャンセルされる場合がある */

muslの実際の実装では、キャンセル可能なsyscall用の内部経路を通す。アーキテクチャ固有のアセンブリも関係し、キャンセル要求との競合やsyscall中断を扱う。キャンセル状態やタイプ、関数ごとのPOSIX仕様によって挙動は変わる。

深掘り：キャンセルポイントはなぜlibcの責務なのか

POSIXスレッドのキャンセルは「要求した瞬間に強制終了」ではない。標準の遅延キャンセル（deferred cancellation）では、pthread_cancel() は対象スレッドに要求を送るだけで、対象がキャンセル有効の状態でキャンセルポイントに達したときに処理される。read() はPOSIXが定めるキャンセルポイントの一つである。

具体例：パイプからの読み取り待ち

/* スレッドA */
char buf[64];
ssize_t n = read(pipefd[0], buf, sizeof buf);
/* キャンセルが成立した場合、ここには戻らない */

/* スレッドB */
pthread_cancel(thread_a);
pthread_join(thread_a, &result);
/* 成功したキャンセルなら result == PTHREAD_CANCELED */
  1. スレッドAは空のパイプでread()を呼び、データ待ちでブロックする。
  2. スレッドBがpthread_cancel(thread_a)でキャンセルを要求する。この呼び出しが成功しても、対象の終了完了を意味しない。
  3. muslのキャンセル処理が、対象スレッドの状態とブロック中のシステムコールを協調させる。キャンセルが有効で条件が満たされれば、対象は通常のread()の戻り値を返さず、キャンセル処理へ進む。
  4. 登録済みのpthreadクリーンアップハンドラが実行され、スレッド固有データのデストラクタなどの終了処理を経て、join可能なスレッドならpthread_join()で終了を回収できる。

この例は、デフォルトのキャンセル有効・遅延キャンセル設定を前提とする。キャンセル無効なら要求は保留され、非同期キャンセルは別の挙動になる。また、読み取りとキャンセルの競合時にはデータ転送の副作用なども考慮する必要がある。

カーネルだけでは満たせない契約

Linuxカーネルのreadシステムコールが担当するのは、ファイル記述子からの読み取りとその結果の通知である。一方、キャンセル状態・キャンセル種別・クリーンアップハンドラ・POSIXスレッドの終了結果はユーザー空間のスレッドライブラリが管理する。したがって、libcのread()を生のsyscallに置き換えると、読み取り自体はできてもPOSIXのキャンセルポイントとしての振る舞いが失われ得る。

muslの実装経路

read()（src/unistd/read.c）
↓
syscall_cp：キャンセル可能なsyscall経路
↓
スレッドのキャンセル状態の確認とCPU依存のsyscall実行
↓
Linuxカーネルのreadシステムコール

muslのread.cではキャンセル対応の内部呼び出しを使う。pthread_cancel.c側にはキャンセル処理の調整があり、CPU別のコードも関与する。これは単に「syscallの前後でフラグを見る」だけではなく、ブロックに入る瞬間とキャンセル要求が届く瞬間の競合を扱う必要があるためだ。

設計の要点：カーネルはI/Oを実行し、libcはPOSIX APIとして観測されるスレッドの振る舞いを成立させる。APIの意味論とシステムコールABIは別の層にある。

なぜ設計として面白いのか

  • APIとABIの分離：POSIX APIとLinux syscall ABIは同じものではない。
  • スレッド意味論の実装：遅延キャンセルの判定、ブロック中のsyscallとの協調、終了時のクリーンアップなど、POSIXのスレッド契約をlibcが実現する。
  • CPU依存の隔離：syscallの呼び出し規約をアーキテクチャ別コードに分離する。
  • 移植時の注意：glibcとmuslの実装差や拡張機能の違いを理解できる。

ソースコードを読む

  • src/unistd/read.c — readの入口
  • src/thread/pthread_cancel.c — キャンセル処理
  • src/internal/syscall.h — 内部syscall API
  • arch/ — CPUアーキテクチャ別実装
