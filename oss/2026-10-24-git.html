01概要・基本情報・開発背景

Gitは分散型バージョン管理システム。各クローンが履歴をローカルに保持し、ブランチの作成、履歴の参照、変更の統合を行える。Linuxカーネル開発を背景に誕生し、現在は幅広いソフトウェア開発で使われている。

項目内容
初期開発Linus Torvalds・Linuxカーネル開発コミュニティ（2005年）
実装言語主にC（補助スクリプトを含む）
ライセンスGPL-2.0（配布物のライセンス文書参照）
対象Linux・Windows・macOSなど

開発背景

Linuxカーネル開発で従来利用していたBitKeeperを使い続けられなくなり、高速で分散型のバージョン管理が必要になったことが開発の契機です。 Gitの歴史

02特徴・使いどころ

  • 分散型：通常のクローンは履歴とオブジェクトをローカルに保持し、オフラインでもコミットや履歴参照ができる。
  • スナップショット指向：コミットはファイルツリーの状態を参照し、同一内容のオブジェクトを再利用できる。
  • 軽量なブランチ：ブランチは基本的にコミットを指す参照として管理される。
  • 整合性検証：オブジェクトの内容に基づくハッシュで破損や意図しない改変を検出しやすい。ただし署名なしでは作成者の真正性までは保証しない。

ソースコードの変更管理、チーム開発のレビュー、リリースのタグ付け、ドキュメントの履歴管理、組み込みファームウェアのバージョン追跡など。巨大な生成物や頻繁に変化するバイナリはGit LFSやアーティファクト保管庫との使い分けを検討する。

自由テーマ

05技術Pickup： 内容アドレス指定オブジェクトデータベース

例えば、数百個のファイルがあるプロジェクトで、1ファイルだけを変更するたびに全ファイルを複製すると、履歴の保存容量が増え続けます。また、分散開発では別々のPCにあるデータが同じ内容かどうかを識別する必要があります。

取り上げる意義：Gitはデータの内容そのものから識別子を作り、変わらないオブジェクトを再利用します。履歴の表現、データの同一性、不変データの共有という設計を一度に学べるため、注目します。Git Objects

オブジェクトと参照の構造

Gitは履歴を単なる差分の連続として保存するのではなく、blob（ファイル内容）、tree（ディレクトリ構造）、commit（スナップショットと親コミット）などのオブジェクトを組み合わせて表現する。オブジェクトIDは型・サイズを含むデータから算出したハッシュに基づく。歴史的にはSHA-1を使い、SHA-256形式のリポジトリにも対応する。

branch: main
コミットIDを指す参照
↓
commit
tree ID / parent ID / 作者 / メッセージ
↓ tree
tree
ファイル名・モード・blob/tree ID
↓ blob
blob
ファイルのバイト列

同じ内容のファイルは、同じハッシュアルゴリズムを使うリポジトリ内で同じblob IDになるため、内容を共有できる。変更が発生すると、変更されたblobとそれを参照するtree、そして新しいcommitが作られる。変更されていないオブジェクトは再利用される。

オブジェクトの共有と履歴

実際に確かめる

名前・メールアドレス・時刻を固定し、SHA-1形式の新規リポジトリで再現できるようにする。

git init -b main --object-format=sha1 demo
cd demo
git config user.name 'Example User'
git config user.email 'example@example.com'
printf 'hello\n' > hello.txt
git add hello.txt
GIT_AUTHOR_DATE='2026-11-28T12:00:00+09:00' \
GIT_COMMITTER_DATE='2026-11-28T12:00:00+09:00' \
git commit -m 'first commit'
git cat-file -p HEAD
git ls-tree HEAD
git cat-file -p HEAD:hello.txt

実行結果（Git 2.47.3、ローカル実行・一部整形）

[main (root-commit) 03d3628] first commit
 1 file changed, 1 insertion(+)
 create mode 100644 hello.txt

$ git cat-file -p HEAD
tree aaa96ced2d9a1c8e72c56b253a0e2fe78393feb7
author Example User <example@example.com> 1795834800 +0900
committer Example User <example@example.com> 1795834800 +0900

first commit

$ git ls-tree HEAD
100644 blob ce013625030ba8dba906f756967f9e9ca394464a    hello.txt

$ git cat-file -p HEAD:hello.txt
hello

commitにはtree IDと作者・時刻が記録される。treeにはファイル名とblob IDがあり、blobを読むと元のhelloが得られる。入力やメタデータ、オブジェクト形式が異なるとIDも変わる。

06設計から学べること

  • 不変オブジェクト：内容が変われば別のIDを割り当て、既存オブジェクトを変更せず新しい参照を作る。
    実装・資料：object-file.c · Git Objects
  • 構造共有：同一内容のblobを複数のtreeから参照できる。変更部分だけ新しいオブジェクトにする。
    実装・資料：tree.c · Git Objects
  • 履歴をグラフとして扱う：commitの親参照をたどって履歴を表現する。
    実装・資料：commit.c · git-commit-tree
  • データと名前の分離：変化するブランチ名を不変のオブジェクトIDから分離する。
    実装・資料：refs.c · Git References

設定スナップショットや更新履歴の設計にも応用できる。ただしリアルタイム制約やフラッシュの制約に合わせた実装が必要。
